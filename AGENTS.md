# Prompt Engineering Academy — правила проекта

## Язык и назначение

- Общение с пользователем и пользовательский контент ведутся на русском языке.
- Технические идентификаторы, имена библиотек, типов и файлов сохраняются на английском.
- Проект — статический образовательный портал для людей с базовым опытом работы с AI.

## Источники истины

При расхождении документов использовать следующий приоритет:

1. Последнее прямое указание пользователя.
2. `docs/DECISIONS.md` — подтверждённые и отложенные решения.
3. `docs/REQUIREMENTS.md` — обязательные требования и критерии приёмки.
4. Предметные документы в `docs/specs/`.
5. `docs/PRODUCT_SPEC.md` и `docs/TECH_SPEC.md`.
6. `docs/IMPLEMENTATION_PLAN.md` и `docs/TEST_PLAN.md`.

При обнаружении расхождения не выбирать вариант молча: остановить затронутую работу, записать противоречие и запросить решение пользователя.

## Границы MVP

- Стек: Astro + React + TypeScript.
- Публикация: публичный репозиторий и GitHub Pages.
- Нет backend, базы данных, регистрации, аккаунтов, реального AI API и секретных ключей.
- Не добавлять функции, которых нет в `docs/REQUIREMENTS.md` или подтверждённом решении пользователя.
- Возможные улучшения не входят в MVP и не должны попадать в реализацию без отдельного одобрения.

## Открытые решения

Перед затрагивающей их реализацией запросить решение пользователя по пунктам со статусом `OPEN` в `docs/DECISIONS.md`, в частности:

- визуальная система;
- CSS/UI-подход;
- drag-and-drop реализация;
- формулы XP, каталог достижений и награды;
- композиция вместо буквального наследования React-компонентов;
- детали GitHub Pages и способ публикации.

## Разработка

- Делать минимальные, сфокусированные изменения.
- Сначала добавлять или обновлять проверку поведения, затем реализацию.
- Scoring engine держать в чистых TypeScript-функциях без зависимости от React.
- Inline-упражнения должны быть автономными React-островами; итоговый тест — одним React-островом.
- Не использовать Redux, Zustand, backend storage или AI API без изменения утверждённых требований.
- Доступность — часть поведения: клавиатура, видимый фокус и кнопочная альтернатива drag-and-drop обязательны.
- Поведенческие изменения должны сопровождаться обновлением требований, спецификаций и тестов.

## Проверка

- Каждый критерий приёмки должен иметь воспроизводимую проверку.
- Перед полным набором тестов сначала проверять разрешение Node.js/npm и минимальный representative test.
- Использовать Vitest для scoring и unit tests, React component tests, Playwright для E2E и accessibility-проверки.
- Проверять production build и опубликованный GitHub Pages URL, когда публикация будет отдельно разрешена.
- Не объявлять работу завершённой без свежих результатов проверок.

## Git и внешние действия

- Не выполнять `git init`, commit, push, создание репозитория, публикацию или изменение GitHub Pages без отдельного прямого запроса.
- Не добавлять секреты, реальные учётные данные или локальные конфигурации в репозиторий.
- Сохранять несвязанные пользовательские изменения.
