## 1. Цель

Браузерная проверка готовой сборки: `npm run test:static-browser`, конфигурация `playwright.static.config.ts`, сценарий `tests/static/production.spec.ts`. Ожидается 1/1 без ошибок страницы/консоли, неудачных запросов и запросов ресурсов вне `/acceptance-preview/`. Отдельно проверяются ответ 200 и тип `image/svg+xml` для значка вкладки, все девять страниц, сохранение результата встроенного упражнения 0%/100% и светлой темы после перезагрузки, итог 0%/0% после 12 пропусков, корректный адрес рекомендации. Проверка выполняется на готовых файлах, без сервера разработки; другие браузеры и опубликованное окружение не покрывает.

Проверка файлов готовой сборки: `npm run test:static` и `npm run check:static`. Ожидаются два результата с `pages: 9`, пустым `failures` и кодом завершения 0 для `/` и `/acceptance-preview/`. Проверяется существование локальных целей `href/src`, модулей React-островов, якорей HTML, ресурсов CSS `url()` и строковых относительных JS-ссылок; выход из заданного префикса считается ошибкой. Префикс предназначен только для теста. Динамические ссылки, `srcset`, исполнение кода и HTTP-обслуживание требуют отдельной браузерной проверки статической сборки, а опубликованный адрес проверяется после разрешения публикации.

Доказать выполнение всех MUST-требований Prompt Engineering Academy локально и, после отдельного разрешения, на GitHub Pages. GitHub Actions для тестов не обязателен.

## 2. Принципы

- Тестировать наблюдаемое поведение и чистые contracts, а не внутреннюю разметку.
- Scoring и state machines проверять преимущественно unit tests.
- Компоненты проверять в обоих режимах.
- Основные пользовательские маршруты проверять production build через E2E.
- Accessibility включает automated scan и ручной keyboard review.
- Каждый defect получает regression test до исправления.

## 11. End-to-end journeys

### E2E-01 — Учебный маршрут

Открыть главную → открыть любую незавершённую статью → ошибиться в первом упражнении → продолжить → попытаться остальные → вернуться на главную → увидеть completion.

### E2E-02 — Двухфазный тест

Запустить тест → отправить/пропустить 12 вопросов → проверить отсутствие оценки → автоматический переход к hints без обоих баллов → исправить eligible либо подтвердить досрочный финал → увидеть оба балла, answer key, recommendations и rank.

### E2E-03 — Восстановление

Начать тест → ответить частично → reload → сравнить IDs/order/answers/phase → завершить.

### E2E-04 — Сброс

Выбрать тему → создать прогресс → отменить reset → проверить сохранение всех данных → подтвердить reset → проверить очистку attempts/completion/results/gamification → reload → проверить, что выбранная тема не изменилась.

### E2E-05 — Keyboard/accessibility

Пройти representative inline и drag-dependent quiz item без мыши → проверить focus order, announcements и отсутствие serious axe violations.

### E2E-06 — Published smoke

На GitHub Pages открыть главную напрямую → article URL напрямую → reload → quiz → выполнить один interaction → проверить assets/console.

При выполнении для каждой проверки и её параметров записывать: requirement/criterion ID, case ID, входные данные, ожидаемый и фактический результат, статус, дату, revision, среду/версии и путь к логу/снимку/ручному протоколу.
- PASS: все ожидания конкретного варианта подтверждены свежими доказательствами.
- FAIL: полученный результат отличается от ожидаемого.
- NOT RUN: проверка ещё не запускалась.
- BLOCKED: указана конкретная причина невозможности проверки; это не PASS.
- Неприменимая ветвь (например partial у TrueFalse) имеет объяснение; нельзя объявлять всё требование неприменимым, чтобы пройти приёмку.

Перед приёмкой сверить множество MUST/SHOULD ID с таблицей: нет пропусков, дубликатов, неизвестных case ID и пустых доказательств для объявленных PASS. Для MUST нужны все связанные проверки, а не одна успешная из списка. SHOULD фиксируется отдельно и не становится блокирующим без изменения требований.
Проверки SC/IV/QA-RULE могут использовать общие fixtures и один тест: таблицы связывают обязательства, а не требуют дублировать реализацию тестов. Полнота таблицы не заменяет редакционную проверку, что каждая часть сложного требования действительно проверена.

Дополнительно проверить все TQ-01–TQ-12 из TECH_SPEC: полное покрытие верхнеуровневых требований не заменяет проверки подробных технических контрактов. Старые SC/QZ/ST и подробные IV/QA строки могут ссылаться на один исполняемый тест; повторный запуск ради разных ID не требуется.

- `presentation.test.ts`, `quiz-order.spec.ts`: QUIZ-003, воспроизводимость на 30 начальных значениях, неизменность оценок/эталонов, сохранение порядка после перезагрузки, в коррекции и разборе; совместимость со старыми попытками без версии представления.

Промежуточный React сервера остаётся отладочным; ошибок страницы нет; неверный ответ показывает 0% и подсказку. Автоматизация: `tests/e2e/dev-runtime.spec.ts`.
- `DEV-RUNTIME-02`: открыть статью без JavaScript; ввод и отправка упражнения отключены. С JavaScript после прокрутки к упражнению ввод доступен и ответ обрабатывается. Автоматизация: `tests/e2e/dev-runtime.spec.ts` и `tests/e2e/core.spec.ts`.
- `feedback.test.tsx`: EX-012, итоговый разбор бюджета показывает выбранные фрагменты, стоимость, полезность, штрафы и формулу; превышение лимита объясняет ноль. До полного разбора эти данные не раскрываются. Выделения галлюцинаций восстанавливаются из результата; симулятор подписывает уровень подготовленного ответа.
- `feedback.spec.ts`: EX-012/PRG-001, отправить ошибочный бюджет, убедиться в отсутствии полного расчёта, отправить окончательный ответ и проверить штраф/формулу. После перезагрузки расчёт не меняется. Выделить утверждение, завершить упражнение и проверить неизменность выделения в разборе после перезагрузки. Внешняя ссылка подписана как материал по теме, а не источник фактов учебной справки; ошибок страницы нет.

Перед релизом повторить проверки конструктора (EX-012/PRG-001): `feedback.test.tsx` различает три причины без исходного ответа; `storage-validation.test.ts` принимает старую общую причину, но отклоняет изменение балла; `feedback.spec.ts` проверяет отсутствие раннего разбора, три причины в финале и неизменность после перезагрузки.

Дополнительные проверки контента: `content.test.ts` сверяет критерии концепций с реальными строками оценщика и подтверждает состав банка 14 повторно используемых / 10 новых сценариев. `authored-rubrics.test.ts` проверяет эталоны семи определений, неполные исходники, регистр/ё, границы чужого слова, 11/12 слов и запрещённую фразу. Это не подтверждает полноту списков отрицаний в реальных рубриках.

Переход рубрик: `rubric-migration.test.ts` проверяет блокировку смешанных версий, адресный перезапуск, сохранение темы/результатов/наград, отсутствие повторной награды и сохранение завершённых результатов. `rubric-migration.spec.ts` проверяет отмену, перезагрузку, подтверждение, новую оценку отрицания и сохранение исправляющей попытки по версии 2. `storage-recovery.spec.ts` проверяет переход теста с версии 1. `authored-rubrics.test.ts` проверяет все заданные списки отрицаний в пределах предложения и восстановление положительного совпадения в другом предложении. Покрытие концепций: `content-gaps.test.ts` проверяет отдельную оценку выбора длины (1 и 2/3), точный/неполный/лишний набор утверждений (1, 0.5, 0), старые записи обоих изменённых заданий и необходимость адресного перезапуска. `content-gaps.spec.ts` проходит ошибки и исправления в статьях, проверяет 100% и перезагрузку.
