# 02 — Exercise Component System

## Назначение

Определить единый typed contract, state model и scoring всех 10 типов. Спецификация не управляет выборкой итогового теста и глобальным прогрессом.

## Архитектурное решение

Утверждена React composition согласно `DEC-018`:

- общий `ExerciseShell`;
- typed definition, answer и result contracts;
- type-specific answer editor;
- pure type-specific evaluator;
- registry, сопоставляющий discriminant type с editor и evaluator;
- общие feedback/result элементы;
- mode adapter для inline/quiz.

`ExerciseShell` является базовой архитектурной абстракцией, но не родительским классом. Конкретные типы переиспользуют shell, state behavior и публичные contracts через composition; пользовательская class hierarchy `BaseExercise` не создаётся.

Добавление нового типа требует нового variant contract, editor, evaluator, registry entry и tests. Оно не должно требовать копирования общей feedback-логики или поведения inline/quiz adapters.

## Общий contract

Каждая definition обязана иметь:

- стабильный уникальный ID;
- один из 10 discriminant types;
- topic ID;
- instruction;
- type payload;
- scoring config;
- hint и explanation;
- accessibility labels для нестандартных controls.

Каждый evaluator возвращает normalized score 0–1, status и объяснимый breakdown.

## Режимы

| Поведение | Inline | Quiz |
|---|---|---|
| State owner | Локальный остров | Quiz reducer |
| Проверка | Результат и минимальная подсказка после submit | Баллы и полный разбор скрыты до finalComplete |
| Retry | Одна попытка после неверного/частичного ответа | Одна correction попытка для неверных, частичных и пропущенных ответов |
| Общий балл | Нет | Есть |
| Persistence event | Результаты без исходного текста | Активная попытка с текстом; после финала только очищенные результаты, см. spec 04 |

## Типы и scoring

### MultipleChoice

- Single: точный вариант = 1, иначе 0.
- Multi: любой неправильный выбранный вариант = 0.
- Только часть правильных без неправильных = selectedCorrect / totalCorrect.
- Полный балл требует точного множества.

### MatchPairs

- Score = correct pairs / total pairs.
- Пара считается правильной только при точном соответствии.
- Full score требует всех пар без ошибки.

### FillTheBlank

- Score = accepted blanks / total blanks.
- Нормализация: trim, collapse whitespace, lowercase, `ё`→`е`, разрешённая terminal punctuation.
- Синоним засчитывается только если включён в accepted answers.
- Typo tolerance выключен по умолчанию. При явном разрешении для отдельного accepted answer допускается ровно одна замена буквы в одном слове длиной не менее 7 букв после нормализации. Длины ввода и эталона равны; все символы, кроме одной буквы, совпадают. Вставка, удаление, перестановка соседних букв и две замены не допускаются. Для коротких слов и многословных ответов приблизительное совпадение выключено. Точное совпадение и явно перечисленные синонимы по-прежнему принимаются.
- Правило применяется только к FillTheBlank; CaseStudy и PromptSimulator не получают допуск опечаток.

### TrueFalse

- Только 1 или 0.
- Explanation обязательно объясняет принцип, а не повторяет label.

### OrderSteps

- Частичный score основан на доле пар элементов в правильном относительном порядке.
- Full score требует точной последовательности.
- Начальный display order перемешивается и сохраняется в попытке.

### CaseStudy

- Каждое задание обязательно содержит непустой исходный плохой промпт в type payload (`initialPrompt`) и инструкцию улучшить именно его. Исходник показан как отдельный блок перед полем ответа в обоих режимах; остаётся доступен при исправлении и разборе. Это авторский контент, не пользовательский текст, и на него не распространяется запрет сохранения введённых ответов.
- Пользователь отправляет полную улучшенную версию, а не описание советов. Критерии связаны с конкретными недостатками исходника; исходный промпт не должен получать полный балл, авторский улучшенный пример должен получать 1. Написание несвязанного запроса с нуля не заменяет этот сценарий.
- Обязательный плохой исходник относится только к CaseStudy. PromptSimulator переиспользует evaluator рубрики, но сохраняет собственный сценарий и не обязан содержать initialPrompt.

- Свободный текст оценивается по сценарным критериям. Каждый критерий бинарный: выполнен или нет; положительные веса в сумме равны 1. Score = сумма весов выполненных критериев.
- Уточнение `EX-011` – ограничения письма (2026-11-04, задача 2): `context-2` и `quiz-context-2` сохраняют один бинарный критерий `limit` весом 0.25, состоящий из двух обязательных проверок `any`. Первая принимает «до 120 слов», «не более 120 слов», «максимум 120 слов», «не длиннее 120 слов», «не превышай 120 слов»; вторая – «без обещания скидки», «не обещай скидку», «не обещать скидку», «скидку не обещай». Каждая проверка ищет допустимое совпадение независимо, поэтому порядок и разделение предложениями не влияют на оценку. Только одно условие, другое число слов или явное отрицание перечисленного условия не выполняют весь критерий. Общий алгоритм, остальные веса и правила попыток не меняются. Это явный словарь вариантов, без обещания распознавать все русские перефразирования. Проверки: `support-limits.test.ts`, `authored-rubrics.test.ts`, `support-limits.spec.ts`; версии и исторические оценки принадлежат spec 04.
- До ответа показываются понятные критерии, их веса и минимум слов. Служебные списки совпадений не показываются.
- Общий каталог проверок: наличие хотя бы одного допустимого понятия; наличие всех обязательных понятий; отсутствие запрещённых формулировок; минимальное количество слов. Критерий задаёт комбинацию этих проверок; все проверки комбинации должны пройти.
- Допустимые слова, фразы и основы слов перечисляются явно. Основа проверяется как начало отдельного слова; произвольный поиск подстроки запрещён. Фразы проверяются как последовательности целых слов. Нет автоматического подбора синонимов, морфологического анализа или исправления опечаток.
- Сценарий объявления (`llm-3` и его адаптация `quiz-context-3`, уточнение 2026-10-14): «текст объявления» выполняет критерий действия; «краткое объявление» и «краткий текст объявления» выполняют критерий формата; «место пока неизвестно» и «место пока не указано» выполняют критерий неизвестного места. Для этих фраз явно заданы отрицания. Запрос «Составь краткое объявление о встрече во вторник в 15:00 по теме план обучения. Укажи, что место пока неизвестно.» получает 1. Рубрика `llm-3` имеет версию 3, контент теста версию 4; сохранённые оценки прежних версий не пересчитываются, перезапуск следует действующему контракту spec 04.
- Нормализация: нижний регистр, `ё→е`, схлопывание пробелов, пунктуация как разделитель. Сначала сохраняются границы предложений (. ! ? и перенос строки), затем нормализуются слова внутри них. Фраза не пересекает границу предложения.
- Явная отрицательная формулировка подавляет положительное совпадение соответствующего понятия в том же предложении. Положительная формулировка в другом предложении может выполнить критерий. Проверка отсутствия запрещённых формулировок применяется ко всему ответу и не отменяется другим предложением.
- Уточнение `EX-011` – отрицания безопасности (2026-11-03): для `safety-2` и `quiz-safety-2` перечисляются оба порядка запрещающей инструкции: «не используй обезличенные данные» и «обезличенные данные не используй», а также «не использовать обезличенные данные» и «обезличенные данные не использовать». То же правило словаря применяется к вымышленным данным; рассмотрению письма как данных/недоверенных данных (`рассматривай`/`рассматривать`); подготовке краткого резюме (`готовь`/`готовить`, `составляй`/`составлять`); подтверждению человека (`требуй`/`требовать`, `запрашивай`/`запрашивать`). Перечень хранится в определениях задания, общий алгоритм сопоставления не расширяется до морфологического или смыслового анализа. Обнаруженный ответ с четырьмя отрицаниями получает 0; замена только положительного обезличивания отрицанием оставляет 0.75; положительный эталон получает 1. Отрицание других действий, например отправки настоящих телефонов, не подавляет положительное обезличивание. Проверки: `safety-negations.test.ts`, `authored-rubrics.test.ts`, `safety-negations.spec.ts`. Веса и правила попыток прежние; версии и сохранение принадлежат spec 04.
- Минимум слов задаётся для задания и проверяется как критерий, а не как запрет отправки непустого ответа. Слово содержит хотя бы одну букву; дефис внутри слова допустим, отдельные числа и знаки не увеличивают длину. Последовательные одинаковые нормализованные слова считаются один раз. Понятие не даёт повторных баллов за повторы. Автоматическое распознавание бессмысленного текста не обещается.
- Полный разбор: критерий, статус, вес, начисленные баллы, найденный фрагмент либо причина незачёта, полное объяснение и один цельный улучшенный пример. Иные формулировки допустимы. После перезагрузки цитаты не восстанавливаются согласно spec 04.
- Интерфейс прямо сообщает об учебной проверке по заданным правилам, а не о понимании текста настоящей моделью.

### PromptSimulator

- Использует общий механизм CaseStudy с отдельными критериями сценария. Каждое задание содержит фиксированную ситуацию, исходные данные и цель; произвольная тема не поддерживается.
- Уточнение `EX-011` – исходные данные объявления (2026-11-07, задача 3). В `llm-3` и `quiz-context-3` критерий `context` весом 0.25 выполняется при двух независимых совпадениях. «Во вторник в 15:00» задаёт день и время. «План обучения», «плану обучения», «плане обучения» и «плана обучения» задают тему. Словарь исключает заданные варианты явного отрицания темы в том же предложении, например «а не план обучения». Оба совпадения допустимы в разных предложениях. Частичный пример предлагает сверить детали с исходными данными. Сильный пример содержит день, время, тему и обозначение неизвестного места. Проверки в `authored-rubrics.test.ts` и `simulator-wording.spec.ts`.
- На задание подготовлены ровно три фиксированных ответа: weak при `0 <= score < 0.4`, partial при `0.4 <= score < 0.8`, strong при `0.8 <= score <= 1`. Уровень определяется по неокруглённому score. Один уровень всегда выбирает один и тот же текст.
- Strong не означает `correct`: полностью верное упражнение требует score = 1.
- Постоянная пометка: «Учебная симуляция: заранее подготовленный пример, выбранный по результатам проверки вашего промпта». Текст появляется целиком, без имитации печати и сетевого обращения к AI.
- В статье подготовленный ответ виден после отправки; это специальное правило симулятора. Полная рубрика и эталон остаются скрытыми до окончательного ответа. В тесте подготовленный ответ скрыт до finalComplete.
- Полный разбор: критерии и баллы, уровень, 2–3 сценарных пояснения о последствиях выполненных/невыполненных критериев и один улучшенный пример.
- Пояснения выбираются по фактическому breakdown в заданном автором порядке, не только по уровню. Для каждого достижимого сочетания критериев контент обеспечивает 2–3 применимых пояснения. Нельзя приписывать фиксированному примеру индивидуальную генерацию по словам пользователя.

### SpotTheHallucination

- Пользователь выбирает заранее размеченные смысловые фрагменты утверждений.
- В задании есть короткая справка, достаточная для проверки всех утверждений, и ссылка на источник. Инструкция требует оценивать по предоставленным данным.
- При N неверных утверждений, T правильных выделениях и F ошибочных выделениях score = max(0, (T - F) / N). N > 0; один фрагмент выбирается только один раз.
- Полный балл требует точного набора. Например, N=4, T=3, F=1 даёт 0.5.
- До исправления одна подсказка о способе проверки без указания нужного фрагмента.
- В полном разборе для каждого утверждения показываются выбор пользователя, правильность и объяснение с отсылкой к месту справки; в тесте только после finalComplete.

### PromptBuilder

- Заданы явные места: роль, контекст, задача, формат либо необходимые для сценария разделы. Если порядок внутри раздела важен, места нумеруются.
- Пропущенное место остаётся пустым и не сдвигает остальные. Одно место принимает один блок, один блок нельзя дублировать.
- При N обязательных блоков, C блоках в правильных местах и E лишних блоках score = max(0, (C - E) / N).
- Обязательный блок не на своём месте даёт 0 за это место, но не считается повторно лишним. Лишним считается выбранный блок вне обязательного набора задания.
- Breakdown различает пропуски, неверные места и лишние блоки. Полный балл требует заполнить все обязательные места без лишнего. N=4, C=3, E=1 даёт 0.5.
- Причины сохраняются как `missing`, `wrong`, `forbidden` соответственно; полный разбор читает их из результата, поэтому не зависит от сохранения ответа редактора. В старых результатах общая причина `wrong` допустима при неизменных баллах, весах и выполнении критериев. Интерфейс предупреждает, что такие записи не содержат точного различения причин; исторические баллы не пересчитываются.

### ContextBudget

- Фрагмент имеет положительную целую учебную стоимость, неотрицательную полезность и признак distractor. Для distractor полезность равна 0, штраф строго положителен и задан в единицах полезности. Числа учебные, не расчёт токенов конкретной модели.
- Uopt > 0: максимальная полезность среди наборов в пределах бюджета. Хотя бы один полезный фрагмент помещается в бюджет.
- При превышении бюджета score = 0. Иначе score = max(0, (сумма полезности выбранного - сумма штрафов) / Uopt).
- Любой оптимальный набор без distractors в пределах лимита даёт 1; единственный эталонный набор не требуется.
- До отправки видны стоимости, занятый объём, остаток и превышение. Полезность, штрафы и признаки distractor раскрываются только в полном разборе.
- Превышение не блокирует отправку: заранее видно «Лимит превышен. Если отправить этот набор, результат будет 0 баллов». Отправка расходует попытку, первая допускает одну коррекцию.
- Пустой набор не принимается, попытка не расходуется: «Выберите хотя бы один фрагмент».
- Полный разбор показывает выбор, стоимость, полезность, штрафы, расчёт и один оптимальный пример с указанием допустимости равноценных решений. Превышение явно объясняет нулевой балл.

## Feedback rules и попытки

- Для всех типов: score = 1 означает correct, 0 < score < 1 partial, score = 0 incorrect. Округление подписи не меняет статус.
- В статье после первого неверного/частичного ответа доступны результат, краткое объяснение принципа и одна минимальная подсказка без точного решения.
- Для всех 10 типов разрешена ровно одна исправляющая попытка при score < 1. Первый правильный ответ сразу завершает упражнение и открывает полный разбор.
- Исправленный ответ проверяется целиком; результат заменяет первый даже при ухудшении. Первый результат сохраняется отдельно.
- Исходный ответ подставляется в редактируемое поле, можно менять всё. Над полем постоянно видно предупреждение о последней попытке и замене балла; кнопка «Отправить окончательный ответ», без дополнительного окна.
- После исправления видны окончательный балл, сравнение с первым, точное решение и полный разбор. Общего счёта для упражнений статьи нет.
- Пустая отправка не расходует попытку, не даёт XP и completion. В текстовом поле пустота определяется после удаления пробелов; непустой слабый текст оценивается рубрикой. У OrderSteps исходная непустая последовательность может быть отправлена без перемещений. Частично заполненные наборы оцениваются по своим формулам.
- В тесте в первой фазе нет status/explanation; между фазами только eligibility и минимальные hints. Числовые баллы, точные ответы, полный breakdown и подготовленные ответы симулятора доступны только после finalComplete всего теста, не после отдельной коррекции.
- Пропуск является действием quiz adapter: score=0, incorrect, отдельный признак skipped. Пустая отправка не становится пропуском автоматически.
- Error/partial/correct не обозначаются только цветом.
- Правила восстановления текстовых полей принадлежат spec 04.

## Прокрутка при перетаскивании

Уточнение приёмки от 2026-10-08 по DEC-037/038: MatchPairs показывает одну текущую ячейку слева и описания справа при внутренней ширине упражнения от 42rem, вертикально при меньшей ширине. Пропорция панелей 2:3. Автопрокрутка этого типа выключена при любой ширине. Для визуальной копии используется `DragOverlay`, исходник остаётся на месте. Копия имеет постоянный position:fixed в локальных стилях, скрыта вне переноса и не влияет на высоту при подключении/удалении временных библиотечных стилей. PromptBuilder и OrderSteps сохраняют `AutoScroller` с `acceleration: 6` и `Feedback` с `feedback: 'clone'` и прежнюю компоновку. Восстановление фокуса использует `preventScroll: true`. Глобальная плавная прокрутка и принудительный возврат страницы после переноса не добавляются. Проверяемые границы: `DND-SCROLL-01/02/03` и `EX-AC-017`.

## Interaction rules

Уточнение DEC-039 (2026-10-09): MatchPairs использует общие `DragItemView` и `DescriptionView` для исходной строки и копии. В копии сохраняются ручка, промежуток, отступы кнопки, состояние выбора и типографика; оболочка не добавляет собственные отступы/рамку/фон. Размеры копии задаёт библиотека по исходнику. Визуальные компоненты не регистрируют датчики и идентификаторы переноса в копии; её содержимое inert и aria-hidden. Проверяемое совпадение геометрии при захвате задано в `DND-TEXT-01`, проверка `drag-text-geometry.spec.ts`. Канонический ответ и правила отмены/назначения неизменны. Разная ширина ячейки назначения может давать другие переносы после отпускания; это не тот же дефект, что смещение текста при появлении копии.

- Каждый editor поддерживает keyboard path.
- MatchPairs, OrderSteps и PromptBuilder имеют buttons для выбора/перемещения.
- В выпадающих списках PromptBuilder промежуточные значения при переборе стрелками не освобождают другие места. В MatchPairs переключение механизма вообще не изменяет пары; назначение кнопкой либо переносом атомарно заменяет связь. После назначения одно и то же описание остаётся не более чем в одном месте.
- Touch path не требует hover.
- Focus после submit переходит к feedback heading/status, затем пользователь может вернуться к editor.
- DnD реализуется через локальный `DragAdapter` на текущей линии `@dnd-kit/react` и необходимых напрямую импортируемых API `@dnd-kit/dom`; legacy `@dnd-kit/core` не используется без нового решения. Версии фиксируются после свежей проверки официальных релизов.
- `DragAdapter` переводит mouse/touch gestures в те же semantic commands, что и button/keyboard path, и не владеет canonical answer state. Conceptual commands: `OrderSteps.moveItem(itemId, targetIndex)`, `MatchPairs.connectPair(leftId, rightId)`, `PromptBuilder.placeBlock(blockId, slotId, targetIndex)`.
- На один экземпляр упражнения приходится одна DnD context/область; глобальный provider приложения не создаётся.
- Invalid/cancelled drop не меняет answer. После переноса восстанавливается логически связанный focus, а изменения объявляются по-русски через live region.
- После `submit`/`review` отправленный/current draft становится immutable и disabled согласно state model. Если state machine разрешает inline retry или quiz correction, она открывает новый editable draft, для которого DnD и alternatives снова работают; quiz feedback раскрывается только на разрешённой фазе. Scoring engine получает только итоговый answer и не зависит от DnD, DOM или React.

Кнопочная и keyboard-friendly альтернатива обязательна и позволяет получить любой достижимый результат при выключенном DnD.

## Configuration validation

Build/test должны отклонять:

- duplicate ID;
- неизвестный type/topic;
- пустой correct set;
- rubric с неверной суммой weights;
- ContextBudget без достижимого допустимого ответа;
- MatchPairs с неоднозначными duplicate keys;
- missing hint/explanation;
- quiz item без serializable payload;
- рубрика с неположительным весом, неизвестной проверкой или пустыми понятиями;
- CaseStudy без непустого initialPrompt, инструкции улучшить его либо с исходником, получающим score=1;
- симулятор без трёх ответов или достаточных применимых пояснений;
- упражнение на галлюцинации без справки, источника или неверных утверждений;
- сборка без обязательных блоков/однозначных мест;
- бюджет с Uopt <= 0, неположительной стоимостью либо неположительным штрафом distractor.

Авторы рубрик обязаны подготовить принятые и отвергаемые примеры, включая отрицания, совпадения внутри чужих слов и альтернативные формулировки. Эталон каждого задания должен получать score=1.

## Критерии приёмки

### Последовательный интерфейс MatchPairs (DEC-037)

- Все механизмы доступны переключателями-кнопками с обозначением выбранного состояния. Одновременно показана одна ячейка; назначенные пары доступны в общей текстовой сводке, без обозначения правильности до разрешённой проверки.
- Нажатие описания и перенос в текущую ячейку вызывают одну команду назначения. Связь можно очистить в текущей ячейке или сводке. Одно описание занимает не более одного механизма; повторное назначение снимает прежнюю связь.
- Переключение механизма не изменяет canonical answer и не расходует попытку. Само назначение не проверяет правильность. Пустая отправка, частичный ответ и единственное исправление сохраняют существующие правила.
- Отправленный ответ блокирует переключение, назначение, очистку и перенос; сводка всех пар остаётся читаемой. Разрешённое исправление снова включает редактор.
- При внутренней ширине упражнения от 42rem ячейка и описания стоят рядом в пропорции 2:3, ниже идут последовательно. Для текущего описания заранее резервируется высота по самому длинному варианту. У механизма один реальный заголовок, резервные копии скрыты и не являются заголовками. Рукоятки имеют подписи «Перетащить описание: [текст]». Исходник не удаляется из потока при переносе: локальный DragAdapter использует библиотечный DragOverlay, постоянно вынесенный из потока локальными стилями; автопрокрутка для MatchPairs выключена. Другие типы сохраняют своё поведение.
- Клавиатура использует обычные кнопки (Tab, Enter/Space). Изменение ответа объявляется по-русски. Отмена и перенос вне цели не меняют ответ; focus возвращается без прокрутки.
